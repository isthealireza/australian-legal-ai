## Published to WF5

- **`Match Reply to Matter` is now a pure normaliser.** No `matter_id`, no `action_id`, no `matched`. It reads only immutable Gmail event data, satisfying your D5 constraint by construction rather than by convention.
- **`Build Reply Context` holds `resolveReply`** — pure, deterministic, no clock, no randomness, byte-identical to the tested function. All seven policy rules implemented.
- **`Reply Matched?`** now gates on `has_event` (does the item have a message id at all).
- **`Sender Verified?`** now gates on `decision === 'ACCEPT'`.
- **`Log Inbound`: `append` → `appendOrUpdate` matched on `idempotency_key`.** This is the fix for the defect you identified. The key was being written and never matched on, so a replay appended a second row. Duplicate suppression is now doubled: the DUPLICATE decision keeps the whole write branch from running, and the write itself can no longer append a second row even if it did.
- **`Log Unmatched Reply` event_id** gains the random suffix.
- **Sender address extraction hardened.** Structural review flagged that with `simple: false` the Gmail node can deliver `from` as an object; `String()` on that yields `"[object Object]"`, which would have poisoned the party check and refused every reply. Extraction now handles string, array and object shapes and carries a `from_parse_ok` flag.

## Two things I decided that you should overrule if you disagree

**1. Rule 2 applied to tag sets, not single tags.** C7 names two matters in the unquoted
body, one of them the thread's. I treat a tag set that *contains* the thread's matter as
context, not conflict — so C7 accepts on THREAD. A tag set naming *only* other matters is a
conflict, so C3 and C8 block. Without that reading, C7 would block and your "preserve the
thread-based match" requirement would fail.

**2. Condition 4a, which is mine and is not in your list.** Your rule 4 would have accepted
C9: the tag is in the unquoted body, the matter exists, and the sender genuinely is a party
to it. To reach your required `NO_AUTHORITATIVE_BASIS` I added: with no usable thread, a
tag is authoritative only if the sender is a party to exactly one matter, or the tag is in
the **subject**. It is marked `AWAITING OWNER REVIEW` in the node. The cost is friction —
a counterparty on several matters who starts a fresh email with the tag in the body only
will be refused and you will be told why.

## What remains unproven

**Sheets write-level idempotency has not been exercised.** The harness writes nothing, so
R2–R4 prove the *decision* produces no write, and the `appendOrUpdate` change is verified
by configuration, not by observing two runs against a real sheet. Proving it properly needs
one controlled replay against a throwaway tab, which touches your spreadsheet — your call,
not mine.

Also still untested in anger: the WF3 vision branch, `Log Send Intent`, `Mark Send Failed`,
and WF4 gate checks 6.5–6.7.

Three notes from the structural review, none breaking: the compatibility fields
(`matched`, `sender_verified`, `unverified_kind`, `unverified_reason`) are emitted and read
by nothing, so their comment is stale; the `write_log_inbound` / `write_append_action` /
`write_touch_matter` flags are computed but no node reads them — routing is done purely by
`decision === 'ACCEPT'`, so they are decorative and will drift; and DUPLICATE shares the
blocked path, which is intentional and special-cased in the Telegram text and severity.
